本仓库是 Monorepo，在根目录运行 `turbo ls` 查看各包信息。

## 本地代理上下文

`AGENTS.md`、`.agents/`、`docs/`、`.scratch/`、`.codex/`、`GLOSSARY*.md` 及其他代理规划或上下文文件只在本地工作区使用。不要将它们纳入 Git 跟踪，也不要在 `.gitignore` 中为它们添加例外。

## 工作约定

以下约定与本地 Spec、Ticket、ADR 等权威文档冲突时，以权威文档为准。

### 包与脚本

- **包边界**：文件系统读写限于当前包。跨包使用代码或资源时，声明依赖并通过该包的公开 `exports` 访问。跨包任务由根目录的 Turbo 或 pnpm 编排。不要用根目录定位器、跨包物理路径或 `@boundaries-ignore` 绕过包边界。
- **开发自动化**：除临时脚本外，维护脚本一律放在所属包的 `scripts/**/*.ts`，使用可擦除的 TypeScript 语法。将它们纳入该包的非构建 TypeScript 项目，接受格式检查、lint 和类型检查，并排除在产品构建产物之外。普通 Node 自动化脚本由 Node 直接执行。临时脚本放在临时目录。
- **任务归属**：优先用工具的原生配置表达任务。直接命令和简单的 `&&` 串联写在所属包的 `package.json` 中，只有逻辑复杂时才新增 TypeScript 脚本。
- **任务职责**：在 `package.json` 中新增脚本时，同时在所属包的 `turbo.json` 中声明任务，为它指定唯一且准确的职责。职责缺失、未知或冲突时，检查必须失败。可按需添加其他标签。子包维护自己的任务和包标签，包标签不能代替任务职责。根包维护自己的任务和全局规则。
- **任务依赖**：用 Turbo 原生任务图声明依赖。声明了职责的无命令聚合节点必须能通过依赖到达可执行任务。仅用于连接依赖的必要节点可以不声明职责。脚本改名或删除时，一并清理失效的任务定义和引用。
- **按需任务**：需要单独选择执行，且不属于现有专门职责的任务，标记为 `work:on-demand`，仍须通过全仓校验。验证正确性、兼容性或可发布性的工作必须进入正式验收，可以作为其中一个步骤。不得通过给任务改名或将其标为按需任务来跳过验收。

### 检查与验收

- **公共命令**：`check`、`check:heavy`、`check:full` 和 `fix` 共用一套任务校验和执行逻辑，按任务职责选择执行范围。CI 直接调用这套实现，并校验四个公共命令是否调用了对应入口。开发和调试时可以直接运行包内的具体任务。
- **逐步验收**：日常用包内检查或 `pnpm check` 做轻检查。交付前用 `pnpm check:full` 完成轻重两层验收。
- **验收入口**：每项验收只保留一个正式入口和一份实现，供开发、CI 和发布共用。仅供内部调用的参数化步骤留在这份实现中。
- **生产链路**：开发、回放和端到端验收共用生产处理链路和制品，入口和配置可以不同。同类流程只维护一份实现，迁移完成后删除旧链路。报告验收结果时写清实际运行的范围，不能把局部测试算作全链路验收。

### 测试

- **测试范围**：单元测试覆盖业务逻辑的正反两种情况，只保留必要的用例。不要编写只检查某段文档或某个文件是否存在的测试。为彻底删除旧功能而写的临时回归测试，最好放在可丢弃的分支中，删除完成后必须清理。
- **测试写法**：优先在用例中直接使用测试运行器的原生断言和普通循环。异步步骤及其等待逻辑也尽量写在用例中。几行相似的测试代码可以保留。只有确需共用、提取后更易维护时，才将职责明确的测试代码单独提取出来。
- **共用测试代码**：项目自己编写的共用测试代码由所属包维护。随模板交付的默认测试代码由对应的模板源维护。共用代码须纳入所属包的格式检查、lint、类型检查和相关行为测试，并列入相应任务的缓存输入。

### 实现与维护

- **按需设计**：设计安全边界等机制时，先明确它解决的实际问题。当前需求用简单实现就能满足时，保持代码简单，等新需求出现再重构。
- **用户界面**：用户可见的界面不得暴露内部实现细节。
- **持久文档**：以代码和少量权威文档为依据。只有得到明确许可时，才新增或修改持久文档。过程记录和临时方案放在临时目录。
- **彻底迁移**：替换旧实现时，同步删除失效的文档、逻辑和代码。只有任务明确要求兼容旧行为或暂时绕行时，才保留相应内容。
